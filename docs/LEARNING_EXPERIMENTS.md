## Learning assessment

Before this slice, the Guide taught the first send/read/save path, offered reference explanations, and linked to Practice. That supported introductory understanding and interview recall but did not require visitors to predict an outcome, inspect evidence, or explain a causal result. The implemented guided experiments now require predictions and actual state comparisons. A populated canvas, a correct quiz answer, an enabled advanced policy flag, or a completed local experiment is insufficient evidence that a visitor understands production Kafka deeply.

This slice implements five causal experiments using the existing browser simulator. They teach partition-local order, group checkpoints, replay, skipped application work, ownership limits, and retry identity. They do not certify broker operations, distributed timing, replication catch-up, transaction visibility, external side effects, Connect, Streams, schema enforcement, or security. Those remain documented production study boundaries in [KAFKA_KNOWLEDGE_AUDIT.md](KAFKA_KNOWLEDGE_AUDIT.md).

## Interaction contract

- Add a separate **Guided experiments** layer on `/guide` after the original one-record exercise. Each experiment uses a native keyboard-accessible disclosure and starts collapsed. The original Send example / Read record / Save progress path and its `order-7F3K9` / `order-created` sample remain intact.
- Each experiment presents **Predict**, **Run**, **Observe**, and **Explain**, followed by a common interview follow-up and an explicit local-simulation boundary. Require a prediction selection before Run; an incorrect prediction must still allow the learner to run, compare, and revise their understanding.
- Merely opening a disclosure, choosing a prediction, reading an explanation, or clearing learning progress must not change simulator state. Show a visible notice next to Run that the action replaces the current simulator workflow with a small paused experiment; this explicit Run action authorizes the simulator reset. Practice answers remain intact.
- Prepare a deterministic bounded fixture through existing store/core actions, capture its actual **Before** evidence, execute the experiment through those same actions, and capture actual **After** evidence. Reading and processing can be deliberate bounded synchronous actions; no automatic producer is started. Result values must be derived from actual records, group positions, delivery attempts, assignments, and events. Expected values belong in the explanation, never in fabricated observed counters.
- Show selected group, partition, offsets/LEO, record identity, attempt/outcome, and ownership only where relevant. Label comparisons as captured run evidence so later workflow changes cannot make a stale result appear to describe the live canvas. Link to Flow and relevant Customize actions for learner inspection and further experiments.
- Comparison tables keep readable columns with a `540px` minimum width inside their local horizontal overflow region. On narrow screens, show a swipe hint and a labelled, keyboard-focusable scroll container; the page itself must not overflow horizontally. Learners can reach Before/After/After commit columns with touch or keyboard without losing labels.
- Persist only bounded learning progress in independent versioned browser storage `kafkalab:learning:v1`: stable experiment ID, selected prediction, and whether the experiment was completed. Validate IDs and prediction choices; unavailable/invalid storage falls back to usable in-memory progress. Restoring progress does not run an experiment or reset simulator state. Clearing learning progress does not clear simulator/chart state or Practice answers, and simulator reset does not clear learning progress.
- **Completed** means the learner ran that local experiment; it must not be presented as a mastery score. Results, transient timers, and packet positions are not restored as live state after reload.

## Five experiments

| Stable ID / lesson | Prediction and deterministic action | Required actual evidence | Explanation and follow-up |
| --- | --- | --- | --- |
| `keyed-ordering` — Same key, ordered lane | Predict whether three events with the same key will share a partition and receive offsets 0, 1, 2. Reset to a small multi-partition workflow; produce three business events with one key while topology and partitioner stay fixed. | Before: empty logs. After: all three stored message IDs, same key, actual partition and each offset; unchanged other partitions where applicable. | Order and offsets belong to a partition. The local FNV teaching hash differs from actual client partitioners. Follow-up: why can increasing partitions change future routing, and why is there no global topic offset? |
| `replay-before-commit` — Success, crash, replay | Predict whether successfully processed but uncommitted work can be read again. Use the existing Duplicate processing fixture/action or equivalent existing core actions with auto-commit disabled, then crash/restart and poll/process once. | Before: one stored record with application success, current next position 1, committed next offset 0. After: same stored message ID/partition/offset, another delivery attempt, committed offset still 0, duplicate/replay evidence. | Restart resumes from the group checkpoint, so application work may repeat. Follow-up: how would an idempotent handler prevent a repeated external side effect? The browser does not execute that external system. |
| `commit-before-processing` — Save too early, skip work | Predict whether a checkpoint proves application success or deletes the stored record. Use the existing Commit too soon fixture/action: read pending work, commit current position, crash/restart, poll once. | Before: stored 1, read position 1, committed 0, processed 0. After: stored 1, committed 1, processed 0, restarted poll 0, actual skipped/lost delivery event for that group. | A group checkpoint can skip unfinished work after restart while the topic record remains. Follow-up: when should the handler commit, and what delivery tradeoff follows? |
| `worker-scaling` — More workers, one hot partition | Predict whether five consumers can actively own three partitions or split one hot key across all workers. Configure three partitions, append a small same-key batch, then add consumers until there are five. | Before/after: actual partition count, consumer count, assignment map, owners with assignments versus idle consumers, and the hot key's stored partition. With five members and three partitions, at most three own partitions and two are idle; the hot partition still has one owner. | More members do not parallelize one partition. The local assignment is deterministic and synchronous; this does not model production rebalance timing or measure production throughput. Follow-up: what key distribution or partition change could help, and what ordering tradeoff would it introduce? |
| `failure-retry-commit` — Retry the record, then save | Predict whether retry creates another stored record or advances commit automatically. Load the existing failed reference record with manual commit; retry it through the existing retry action, capture the retry result, then expose a separate explicit manual commit step. | Before: actual failed message ID, partition/offset, attempt 1, safe failure reason, committed cursor. After retry: same stored ID/partition/offset and record count, later successful attempt, unchanged committed cursor. After explicit commit: actual group committed cursor advances and record remains stored. | Processing success and saved group progress are separate. Both commit modes stop at the latest failed attempt under the lab safety policy; real Kafka clients can explicitly commit past failed work. Follow-up: when would a retry/dead-letter policy trade ordering for availability? |

## Packet lifecycle and teaching boundary

- Each fresh packet starts from its own event presentation clock, not the age of the enclosing SVG/document animation timeline. Each segment follows its actual edge destination; a produced record can then enter its matching topic-to-partition segment. Every active packet expires within the existing `1800ms` visual TTL and is removed from rendering after its transit. Remounting an existing event cannot extend its original deadline.
- Implementation uses an event presentation clock (`visualStartedAt`), stable generation (`visualRevision`), and a finite deadline. `requestAnimationFrame` paints the packet's SVG transform at `getPointAtLength` along its actual edge geometry, using elapsed time from the original event birth. It paints the exact destination for one frame before removal, with a `64ms` bounded fallback if frames stop. Remounting a still-valid transit can resume only its original remaining life; rebuilt token objects/path changes update geometry without granting a fresh lifetime. Frames/deadline/settle timers are canceled during cleanup and remain transient. The final browser suite verifies actual displacement of the same packet, not merely an animation start value.
- Pause, reset, route unmount, hydration/reload, and background visibility cleanup invalidate old visual transits. Returning to Flow or the foreground cannot replay a frozen packet from an old event. A fresh event after returning starts normally; sending a fresh order while paused still gives a finite transit without starting playback. The 24-token limit and exact event/message/producer/partition/consumer routing remain intact.
- Cleanup changes only decorative activity, never topic records, delivery attempts, offsets, source events, chart history, quiz answers, or learning progress. Reduced motion has no moving packet and retains meaningful text/state.
- Producer → topic → partition illustrates the append teaching path, not the exact Kafka client wire protocol or a central topic-routing broker. Consumer → commit illustrates a group offset checkpoint; no business payload is physically sent to an offset node and commit does not prove application completion.
- Replace wording that says **Awaiting commit means unfinished** with wording that names unsaved group progress. A successful handler can still await commit; read, processed, and committed are distinct states.
